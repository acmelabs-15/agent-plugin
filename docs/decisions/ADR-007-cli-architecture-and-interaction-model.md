# ADR-007 CLI Architecture and Interaction Model

## Context and Problem Statement

`@acmelabs/agx` is a cross-platform CLI with an embedded MCP server for managing AI agent plugins across 4 platforms (see ADR-002 Amendment #1; reduced from 7). ADR-005 established Bun as runtime, ADR-006 established the dependency stack (gunshi for command routing, @clack/prompts for interactive UX, ci-info for CI detection). This ADR defines how the CLI is structured, how commands are organized, and how three execution modes (interactive, CI, MCP) shape user interaction.

The core question: How should the CLI organize its command tree, handle global flags, resolve missing input across execution modes, and map interactive prompts to @clack/prompts components?

## Decision Drivers

- Cross-platform consistency across 7 coding agent platforms
- Three execution modes (interactive terminal, CI pipeline, MCP tool call) must each work correctly
- ADR-002 removed the hosted registry, eliminating the `publish` command
- ADR-003 mandates always-namespace, removing the need for conflict resolution flags
- ADR-006 selected gunshi (command routing), @clack/prompts (interactive UX), ci-info (CI detection), @modelcontextprotocol/sdk + zod (MCP server), @gunshi/plugin-completion (shell completions)
- Validation must be consistent between interactive and non-interactive modes
- AI agents calling the CLI via MCP must receive structured error responses for self-correction

## Considered Options

### Command Tree Structure

- Option A: Flat command list (all commands at root level)
- Option B: Grouped tree with consumer, author, and scaffolding categories (chosen)
- Option C: Deeply nested subcommand hierarchy (4+ levels)

### CI Detection

- Option A: Manual --ci flag only
- Option B: ci-info package with three-layer detection (chosen)
- Option C: TTY detection only

### Missing Input Resolution

- Option A: Always error on missing input
- Option B: Three-tier resolution by execution mode (chosen)
- Option C: Always prompt, hang in CI

## Decision Outcome

Ten interconnected decisions govern CLI architecture and interaction. Each is documented below.

### Decision 1: Command Tree Structure

This Decision 1 is retained for historical reference. All other ADR-007 decisions (D2-D10) remain active.

### Decision 2: Global Flags

Five global flags inherited by all commands via gunshi plugin system:

| Flag | Short | Type | Default | Description |
|------|-------|------|---------|-------------|
| `--ci` | | boolean | auto-detected via ci-info | Full non-interactive mode |
| `--yes` | `-y` | boolean | false | Auto-confirm prompts (keeps spinners/colors) |
| `--json` | | boolean | false | JSON output (data to stdout, logs to stderr) |
| `--verbose` | `-v` | boolean | false | Debug output |
| `--quiet` | `-q` | boolean | false | Errors only |

Behavior rules:

- `--ci` implies `--yes`
- `--quiet` and `--verbose` are mutually exclusive (`--quiet` wins)
- `--json` overrides output formatting
- Output verbosity stack: quiet < default < verbose

**Flag Interaction Matrix:**

| Combination | Prompts | Spinners/Progress | Verbosity | Output Format |
|-------------|---------|-------------------|-----------|---------------|
| *(default)* | Interactive | Active | Normal | Formatted text |
| `--yes` | Auto-confirmed | Active | Normal | Formatted text |
| `--ci` | Error + exit | Suppressed | Normal | Plain text |
| `--json` | Error + exit | Suppressed | Normal | JSON envelope |
| `--verbose` | Interactive | Active | Debug | Formatted text |
| `--quiet` | Interactive | Suppressed | Errors only | Formatted text |
| `--ci --verbose` | Error + exit | Suppressed | Debug to stderr | Plain text |
| `--ci --quiet` | Error + exit | Suppressed | Errors only | Plain text |
| `--json --verbose` | Error + exit | Suppressed | Debug to stderr | JSON envelope |
| `--json --quiet` | Error + exit | Suppressed | Errors only | JSON envelope |
| `--ci --json` | Error + exit | Suppressed | Normal | JSON envelope |
| `--verbose --quiet` | Conflict: --quiet wins | Suppressed | Errors only | Formatted text |

### Decision 3: CI Mode Architecture

Three-layer CI detection using ci-info package (zero deps, 50+ CI vendor support):

1. Explicit `--ci` flag (highest precedence)
2. Environment variable detection via ci-info (`CI`, `GITHUB_ACTIONS`, etc.)
3. TTY detection: `process.stdin.isTTY === false` (lowest precedence)

**--ci vs --yes distinction:**

| Flag | Prompts | Spinners/Colors | Use Case |
|------|---------|-----------------|----------|
| `--yes` | Auto-confirmed | Active | "I trust defaults, just do it" |
| `--ci` | Suppressed | Suppressed | "Running in pipeline" |

`--ci` implies `--yes`. The reverse is not true.

### Decision 4: Three-Tier Input Resolution

Core architectural principle. When required input is missing, behavior depends on execution mode:

| Mode | Missing Required Input | Example |
|------|----------------------|---------|
| Interactive (terminal) | @clack/prompts select/multiselect with valid options | Platform selection via p.autocompleteMultiselect() |
| CI (non-interactive) | Error with flag hint | "Missing --scope. Required in non-interactive mode." |
| MCP (AI tool call) | Error response with options list for agent self-correction | `{ error: "missing scope", options: ["global", "project"] }` |

This pattern applies uniformly: global flags, command-specific flags, wizard inputs.

### Decision 5: Command-Specific Flags

**`add <source>`:**

| Flag | Type | Description |
|------|------|-------------|
| `--scope` | `global` or `project` | Install scope |
| `--platforms` | string (comma-separated) | Target platform IDs (plural) |

**`upgrade [source[@version]]`:**

| Flag | Type | Description |
|------|------|-------------|
| `--version` | string | Target version for pinned upgrade |

Removed: `--conflict` flag. Always-namespace (ADR-003) prevents file conflicts between plugins. Reinstall/upgrade always overwrites own files.

### Decision 6: Interactive Fallback (No Subcommand)

When user runs `agx` with no subcommand in interactive mode:

- Show context-aware `p.select()` menu
- If `plugin.json` present (author project): author commands appear first
- Otherwise: consumer commands appear first
- `new` without type triggers secondary `p.select()` for content types
- In CI mode: show help text (no interactive menu)

### Decision 7: @clack/prompts Component Mapping

12 APIs explicitly tested on Bun 1.3.8 (PASS). 6 v1.0.0 additions (autocomplete, autocompleteMultiselect, box, path, progress, taskLog) confirmed in v1.1.0 source, Bun runtime verification pending.

| Component | Where Used |
|-----------|-----------|
| `p.intro()` / `p.outro()` | Every command entry/exit |
| `p.cancel()` / `p.isCancel()` | Every cancel guard |
| `p.group()` | Multi-step flows: add, init, dev, new agent, new mcp init |
| `p.progress()` | Installing deps, removing sources, checking versions, building |
| `p.spinner()` | Single async operations: fetching, validating, downloading |
| `p.autocomplete()` | Model selection, hook event selection |
| `p.autocompleteMultiselect()` | Platform selection (>5 items), tool selection, content types |
| `p.multiselect()` | Same as above (5 or fewer items) |
| `p.select()` | Scope, transport type, hook type, delegation pattern |
| `p.text()` | Names, descriptions, paths, commands, regex patterns |
| `p.confirm()` | Reinstall, install deps, proceed with upgrade |
| `p.note()` | Package summary, project tree, created content, upgrade summary |
| `p.box()` | Source details in list command |
| `p.taskLog()` | Initial install in dev command |
| `p.path()` | Directory selection in init, build config |
| `p.log.*` | Info, warn, error, success, step messages |
| `p.stream` | Available for streaming build output |

All prompts wrapped in isCI/isTTY guard per Decision 4.

### Decision 8: Validation Rules

16 validation rules for `p.text()` inputs, enforced by Zod schemas:

**Naming (3):**

1. Package name: Must be `@scope/name` format
2. Version: Must be `X.Y.Z` semver
3. Component name: Must match `^[a-z][a-z0-9-]*$` (kebab-case, per ADR-003)

**Uniqueness within plugin project (3):**

1. Agent name unique within this plugin
2. MCP server name unique within this plugin
3. Tool name unique within selected MCP server

**Paths and patterns (3):**

1. Dist dir must not equal content dir (prevent overwriting sources)
2. Hook matcher must be valid glob pattern (eliminates ReDoS risk, CWE-1333)
3. Env var name: `^[A-Z_][A-Z0-9_]*$` (UPPER_SNAKE_CASE)

**Miscellaneous (3):**

1. Tool parameters: `name:type` format
2. Port: 1-65535
3. Agent description: 10 or more characters (helps orchestrator delegation)

**Source validation (4):**

1. npm package source: Must match `^@[a-z0-9-]+/[a-z0-9-]+(@\d+\.\d+\.\d+)?$`
2. Git HTTPS source: URL scheme allowlist -- `https://` only. No `http://`, `file://`, `data://`, `git://`
3. Git shorthand source: Prefix allowlist -- `github:`, `gitlab:`, `bitbucket:` only
4. Local path source: Must resolve within workspace. No `..` escaping workspace root. Path containment enforced.

**Source type detection order:** if starts with `@` then npm package. If starts with `https://` then git HTTPS. If starts with `github:`/`gitlab:`/`bitbucket:` then git shorthand. Otherwise local path.

### Decision 9: MCP Error Response Schema

All MCP tool responses use a common envelope. Error responses MUST NOT include internal paths, stack traces, environment variables, or system information (CWE-209 sanitization requirement).

```typescript
// MCP Tool Error Response Schema
const McpErrorResponse = z.object({
  ok: z.literal(false),
  error: z.object({
    code: z.enum(["MISSING_INPUT", "INVALID_INPUT", "NOT_FOUND", "CONFLICT", "RUNTIME_ERROR"]),
    message: z.string(),
    options: z.array(z.string()).optional(),  // Valid options for self-correction
    command: z.string().optional(),           // Command that failed
    flag: z.string().optional(),              // Flag that was missing/invalid
  }),
});
```

### Decision 10: Common JSON Response Envelope

The JSON envelope shape is part of the public API with semver stability guarantees. All commands use the same envelope. `data` is command-specific but `ok` and `error` are guaranteed.

```typescript
// Success response
const JsonSuccessResponse = z.object({
  ok: z.literal(true),
  data: z.unknown(),  // Command-specific payload
});

// Error response (same shape as MCP errors)
const JsonErrorResponse = z.object({
  ok: z.literal(false),
  error: z.object({
    code: z.string(),
    message: z.string(),
    options: z.array(z.string()).optional(),
  }),
});
```

### Consequences

**Good:**

- Three-tier input resolution guarantees correct behavior in all execution modes without code duplication
- Grouped command tree scales to new content types without restructuring root commands
- ci-info covers 50+ CI vendors with zero configuration
- 16 Zod-backed validation rules catch errors at input time, not at manifest write time
- `--yes` vs `--ci` distinction preserves UX richness when automation is partial
- @clack/prompts component mapping provides full coverage verified on Bun 1.3.8
- Context-aware interactive fallback reduces onboarding friction for new users

**Bad:**

- Every prompt site requires a three-branch guard (interactive/CI/MCP), increasing code volume
- 18 @clack/prompts components create a large API surface to maintain across upgrades
- ci-info adds an implicit behavior layer that may surprise users who expect explicit flag control
- Validation rule count (16) will grow as new content types are added

### Confirmation

- Code review: every command handler must implement the three-tier input resolution pattern
- Integration test: each command tested in interactive, `--ci`, and MCP modes
- Validation test: all 16 Zod schemas tested with valid and invalid inputs
- CI pipeline: `--ci` auto-detection verified in GitHub Actions
- Test count formula: commands x inputs x modes. For 14 commands with average 3 inputs across 3 modes = 126 minimum test paths. Risk-based testing strategy recommended: exhaustive for core paths (add, remove, upgrade), representative for scaffolding commands.

## Implementation Notes

### Three-Tier Guard Pattern (Pseudocode)

```typescript
function resolveScope(flags: Flags, mode: Mode): string {
  if (flags.scope) return flags.scope;
  if (mode === "interactive") return await p.select({ options: ["global", "project"] });
  if (mode === "ci") throw new Error("Missing --scope. Required in non-interactive mode.");
  if (mode === "mcp") return { error: "missing scope", options: ["global", "project"] };
}
```

### Terminal Colors

@clack/prompts v1.1.0 replaced picocolors with node:util styleText. No picocolors is available transitively. Use styleText directly for any terminal color needs outside @clack/prompts components.

### Output Mode Matrix

Exit codes: 0 = success, 1 = runtime error (operation failed), 2 = usage error (invalid input, missing required flags).

| Condition | stdout | stderr | Exit Code |
|-----------|--------|--------|-----------|
| `--json` success | JSON data | logs (if --verbose) | 0 |
| `--json` runtime error | JSON error object | logs | 1 |
| `--json` usage error | JSON error object | logs | 2 |
| Default success | Formatted text | n/a | 0 |
| Default runtime error | Error message | n/a | 1 |
| Default usage error | Error message with flag hint | n/a | 2 |
| `--quiet` success | Nothing | n/a | 0 |
| `--quiet` error | Error only | n/a | 1 or 2 |

## Reversibility Assessment

- [x] **Rollback capability**: Command tree can be reorganized without data loss; commands are stateless
- [x] **Vendor lock-in**: @clack/prompts is MIT-licensed with a stable API; alternatives exist (inquirer, prompts). ci-info is MIT with zero deps.
- [x] **Exit strategy**: Three-tier guard pattern is framework-agnostic; prompt library is swappable behind the guard
- [x] **Legacy impact**: No legacy CLI exists; this is the initial architecture
- [x] **Data migration**: CLI is stateless per invocation; no persistent data affected by structural changes

## Vendor Lock-in Assessment

**Dependency**: @clack/prompts v1.1.0
**Lock-in Level**: Low

### Exit Strategy

**Trigger conditions**: @clack/prompts abandoned or incompatible API break
**Migration path**: Replace prompt calls behind three-tier guard functions; guard pattern is library-agnostic
**Estimated effort**: 2-3 days to swap prompt library
**Data export**: N/A (stateless CLI)

### Accepted Trade-offs

@clack/prompts provides the richest terminal UX of available options (18 components, spinner, progress, autocomplete). The three-tier guard pattern isolates prompt calls, making the library swappable without architectural change.

## Amendments

### Amendment #1: Resource-First CLI Structure and Individual Content Type Management (2026-03-09)

The CLI adopts resource-first (noun-verb) command structure per ANALYSIS-054 research. Each content type is a top-level command group with uniform subcommands:

```
agx plugin    add|remove|list|create
agx skill     add|remove|list|create
agx agent     add|remove|list|create
agx command   add|remove|list|create
agx rule      add|remove|list|create
agx hook      add|remove|list|create
agx mcp       add|remove|list|create
```

**Rationale**: 7 of 9 multi-resource CLI tools use noun-verb with singular nouns (Docker `container`, gh `issue`, AWS `s3`). Tab completion works better with resource-first. Resource-specific operations (like `agx mcp create-tool`) nest naturally. See ANALYSIS-054.

**Scope expansion**: Content types can be added/removed individually (not just as part of a plugin bundle). Sources for individual content types are the same as plugins: npm packages, git repos, local paths.

This supersedes the previous verb-first command tree in Decision 6.
